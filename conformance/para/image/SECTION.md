Method. I read `ref-php/text-wiki/Text/Wiki/Parse/Default/Image.php` and `ref-php/text-wiki/Text/Wiki/Render/Xhtml/Image.php`, then searched the read-only ftml checkout and read `src/parsing/rule/impls/block/blocks/image.rs`, `src/render/html/element/image.rs`, `src/tree/image_source.rs` and `src/test/image_paragraphs.rs`. The harness and the dumper were used read-only, no ftml file was edited and no cargo was run. The fossil is treated as a skeleton throughout, and live truth is used for every disagreement.

Mechanism as corrected. The outer matcher now accepts `[[image ...]]` with an empty head and no longer captures an optional `[[/image]]` closer or a caption body, so any text after the image is ordinary source text and the unmatched closer stays literal. The accepted spellings are still `image`, `=image`, `<image`, `>image`, `f<image`, `f=image` and `f>image` with a case-insensitive name; alignment is still matched case-sensitively, which is live truth (probe p05). The parse rule keeps sources, alignment and the `link`, `style`, `class`, `alt`, `height`, `width`, `size` options and adds `title` first in the option order, rejects a link whose value begins with whitespace directly or after the new-tab star, and bails out to a literal opener when a finished raw `@@...@@` construct appears in the head. The renderer still classifies source URLs against the local-files and resized-images paths, derives the default alt from the last path segment and wraps the image in the anchor and alignment container as before; it now emits `title`, percent-encodes non-ASCII bytes in the `src` and `href` values while keeping authored alt text, leaves fragment-only link targets as bare fragments, and emits compact `<a href="...">` and `<a href="..." target="_blank">` instead of the fossil's padded attribute space. The fixed live attribute order is `title`, `style`, `class`, `alt`, `height`, `width`, followed by a default `alt` and default `class` when those were not authored; the reference already had the trailing defaults and the style/class/alt/height/width order right, so no reordering was needed.

Corrections and classifications. C1, missing `title`, reference bug: live emits `title` (probe p09 and p17, pin `image/basic`), the fossil whitelist dropped it, so the parse rule now carries it and the renderer emits it in first position. C2, caption and `[[/image]]` consumption, fossil-era artifact: the fossil captured a body it never rendered, while live leaves it as text (probes p01 and p02), so the capture group is gone. C3, leading-whitespace link values, reference bug: the fossil accepted `link=" https://..."` and `link="* https://..."` with a broken href, while live leaves the whole opener literal (probes p03 and p04, pin `image/basic`), so those forms now bail out. C4, empty head, reference bug: `.+?` required a nonempty head, while live and pin `image/empty-head` emit an empty-named attachment image (probe p07), so the group is `.*?`. C5, fragment href, reference bug: the fossil prepended a slash to every non-URL link, while live keeps `href="#gif-sucks"` (probe p08, pin `image/basic`), so a leading `#` is exempted. C6, non-ASCII URL bytes, reference bug: live percent-encodes them in `src` and `href` while keeping the authored alt (probe p12, pin `image/nonascii-filename`), so a byte-level encoder was added. C7, raw construct in the head, reference bug: live leaves the opener literal with the raw token rendered in place (pin `image/raw-head-literal`, battery i37-67), so a delimiter check bails out. C8, stray anchor attribute spaces, fossil-era artifact: the same pretty-print artifact corrected in the Table renderer, removed here. The pre-correction bytes are preserved verbatim as `Image.php.before.php` (parse rule, SHA-256 1ee9350c5c0797b3b072483654c64cd34168d5d4f3a35e680b808d481fc2d7fb) and `ImageXhtml.before.php` (Xhtml renderer, SHA-256 0b26c40c92d21a929b68646bf74d482e30b36a9e205fcbe0af5506d4ec3b5248); the corrected files hash to c1d84d89203825574ebc93f5fd16552c409bd7f2a21809a62ef66edf692ea98b and c8389998714767a8c564c4a75b22b7f47cf4a97c1b78a22e88216c89d7e49973 respectively.

The reference render and tokens drivers and the shared dumper were run over it before and after correction with all six battery capture files holding 68 records and matching empty `.err` sidecars, and no driver reported a case error. Remaining disagreements and dispositions. Five battery cases still differ from the dumper under shape normalization. `i37-10-uppercase-align` and `i37-36-attr-width-empty` are candidate ftml divergences IMG-F1 and IMG-F3 below, with live confirming the reference. `i37-37-attr-height` is the candidate ftml divergence IMG-F2 below, hidden from the headline shape count only because attribute sorting removes it. `i37-61-inline-in-text`, `i37-62-blank-line-after` and `i37-65-paragraph-then-image` are frame-level surface owned by the Paragraph rule (rule 39): live probes p01 and p14 show no `<p>` wrapper around text adjacent to an unaligned image, the dumper follows live, and the fossil Paragraph rule wraps the run; this cannot be fixed by editing this rule's two files and is handed to root and the Paragraph owner. No other battery shape disagrees. Attachment existence, file serving, the wjfiles versus wdfiles host and the per-page path slot are serving-layer scope and were normalized away, not corrected. The dumper reported parse errors on 11 battery cases, all literal-opener forms in the `fail` family where the reference and live agree.

Stage candidate ftml findings for root. IMG-F1: ftml treats an uppercase alignment marker as a valid alignment, so `[[F>IMAGE https://example.com/a.png]]` emits `<div class="image-container floatright">`, where live emits the plain `<div class="image-container">`; evidence is live probe p05 (`muse-probe-r2para-img-p05-uppercase-align`, captured HTML and `captures.json`), battery case i37-10 and its dumper record, against pin `test/image/name-case-uppercase` which covers only the unaligned spelling. The reference matches live and I changed nothing. IMG-F2: ftml canonicalizes image attribute order to width before height and class before the default alt, where live emits height before width and the default alt before the default class; evidence is live probes p09, p10, p11, p16 and p17 with their dumper records, plus battery cases i37-01 and i37-37, and the reference matches live on all of them. IMG-F3: ftml emits a bare `width` for `width=""`, where live emits `width=""`; evidence is live probe p11 and battery case i37-36 with their dumper records, and the reference matches live.

Harness matter and scope boundary. The fossil renderer's `:first` source calls `DB_FilePeer` and its `flickr:` source calls `FlickrHandler`, neither of which is stubbed by the root-owned harness. A throwaway case with source `[[image flickr:12345_abc]]` through `batch.php render` returns `{"id":"i37-x-flickr","error":"Error: Class \"FlickrHandler\" not found"}`, and source `[[image :first]]` returns an empty string because no stub page or file exists. Both forms are serving-layer, external-API or attachment-existence paths, so I kept them out of the shipped battery and made no harness edit; root confirmed the disposition and will disclose the gap in R2-PARA.md.

Questions and assumptions. The leading question was whether the `[[image ...]]body[[/image]]` form is a real caption wrapper that live consumes; probes p01 and p02 settle that live emits the body as text and leaves the closer literal, so no assumption was needed. The second question was whether live preserves authored attribute order; probes p10, p16 and p17 settle that live uses a fixed order identical to the reference's, so I deliberately did not reorder the renderer to match the dumper. I proceeded on the standing rule that corpus pins precede probes only where they agree, and used live as the tie-break for the three candidate ftml findings. I assumed the harness's empty page name and the dumper's `some-page` both represent the same serving-layer slot and normalized them rather than changing any rule. The read-only ftml checkout HEAD is the one recorded for the shared dumper, and no later checkout change was re-run here.
