R2-contain shared-harness audit (root, before rule owners' differentials). The container family has process-static document counters that the shared batch harness does not reset per case: Text_Wiki_Parse_Collapsible::$count and Text_Wiki_Parse_Tabview's private static $_counter. The audit inputs are audit-alone.jsonl (three cases a1 collapsible, a2 tabview, a3 div rendered in a fresh process) and audit.jsonl (the same three cases after three leading cases p1-p3 that themselves contain collapsibles and a tabview), with audit-render.jsonl and audit-alone-render.jsonl the two captures and empty .err sidecars. a3 (div) is byte-identical between the two runs, confirming no general cross-case state leak, while a1's collapsible-block ids are 0 in the alone run and 2 in the batch run and a2's tabview/tab ids differ likewise. The ids are presentation-only: live renders random ids for both collapsible and tabview elements and the shared ftml dumper emits its own ids, so every three-way comparison already masks numeric and random element ids, and this leak does not change any structural or display-shape agreement. Root's decision, following the R2-block precedent for addToken's static id counter, is to leave the shared harness byte-unchanged during concurrent rule work and disclose the leak here as a harness matter rather than add a reset mid-run; all rule owners were told to normalize counter-bearing ids in their before/after and three-way comparators and never to score an id shift as a correction. No harness file was edited for this stage.
