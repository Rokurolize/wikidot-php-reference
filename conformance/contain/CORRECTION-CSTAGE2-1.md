# CORRECTION C-STAGE2-1 — Div attribute emission order (REFCORR2 lane, 2026-11-22)

Status: APPLIED in this tree. The reference's Div parse stored a div's attributes sorted by name (the fossil's `ksort`, kept at R2 because the R2 probes' authored orders did not discriminate a ranking); live emits them in a fixed order. The correction builds the emission order explicitly at parse time. Recorded as candidate C-STAGE2-1 in stage2/REPORT-STAGE2.md §5 (the p34 divergence: reference class before id, live id before class; the F-R2-55 family).

## The settling evidence (fresh live probes, all valid, stable, and saved-source-matching)

Eight block-form divs with quoted values, authored in permuted orders, probed 2026-11-22 on sandbox-for-codex (pages muse-probe-refcorr2-diva-a1 to a8; cases and captures in conformance-refcorr2/probe-cases.jsonl and conformance-refcorr2/probe-captures.json). a1 to a4 author class, id, and style in four different orders and live serves all four identically as `<div id="u-b" class="a" style="color:green">`; the order is therefore a fixed ranking, not the authored order. a5 (authored data-z, type, role, style, class, id) serves `id, class, style, role, type, data-z`, fixing the ranking of the five named attributes and placing data-* after them. a6 (authored data-z, data-a, class) serves `class, data-z, data-a`: the data-* attributes keep their authored relative order and are not sorted among themselves. a7 (authored type, role) serves `role, type`, and a8 (authored data-m, id) serves `id, data-m`, both consistent with the ranking. The full rule: emit id, class, style, role, type, in that order, then the data-* attributes in authored order. The frozen stage-2 battery capture p34 (`<div id="u-b" class="a" style="color:green">` against the reference's class-first output) is the same rule on a fifth permutation.

## The correction (reference)

Parse/Default/Div.php only: the `ksort($args)` call is replaced by an explicit construction of the emission order (the five ranked names in live's order, then the data-* entries in collection order). The correction is realized in the parse, not the renderer, because the parse's sort is the point where the data-* authored order is destroyed; a renderer-side reorder could not recover it (probe a6). The renderer is unchanged for this candidate and continues to emit the stored order.
