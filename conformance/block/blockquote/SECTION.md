# R2 Blockquote section: differential and correction (2026-11-20)

Mechanism as corrected. The Blockquote rule in this reference owns the `>`-prefixed native quote line, not the `[[blockquote]]` block form. Layer ownership is as follows: the preproc and newline layers decide that a `>` run anchors at line start and hand the marker run to this rule; this rule recognizes a run of adjacent `>` markers (depth is the count of markers in one run, so `>>` is level 2 while `> >` is level 1 with a literal `> ` in the body), computes the start/end token stack, and lays out the newlines around those tokens; the Paragraph rule downstream wraps the body text in `<p>`; the Xhtml renderer here emits the `<blockquote>` tags. The other standing facts were not relitigated: a space-prefixed marker line is ordinary text (an attempted saved-page probe with source ` > q` could not be stored verbatim because Wikidot strips the leading space on save, which corroborates the settled fact), and the tight quoted-include shapes from the F-G14-1 relay stay pinned. The `[[blockquote]]`, `[[quote]]`, attributed and unterminated block forms are literal text on live Wikidot, settled by ftml's corpus pin test/blockquote/block/wikidot.html and confirmed by four cached live probes (block-form, quote-alias, block-attrs, block-unterminated); the fossil already renders them literally, so this rule makes no claim over them and no change for them. After correction the parse rule still emits one `Blockquote` token pair per level with the token option shape `{type, level}` unchanged, and the render rule still emits `<blockquote>` / `</blockquote>` with the optional `css` class, so all downstream rules and the token contract are preserved.

Corrections made, with classifications. C1 (fossil-era artifact) removed the render-side pretty-print padding: the fossil built `$pad` of four spaces per nesting level and prefixed every `<blockquote>` and `</blockquote>` with it, while live saved pages and ftml's Wikidot-layout render have no such indentation at any depth. The `level` option is left in the token for compatibility but is no longer consulted for output. C2 (fossil-era artifact manifesting as a reference bug) suppresses empty quote containers in the parse rule: a matched quote run whose every body line is whitespace-only is consumed with its paragraph break but emits no Blockquote tokens. Live drops an empty quote container entirely (cached probe muse-probe-r2block-bq-marker-space-before-text with source `> \nX` renders only `<p>X</p>`, and the frozen notes probe muse-probe-r2notes-fnb-quote-empty-line shows the same on a `> ` line followed by a blank line), and ftml's dumper agrees, whereas the fossil emitted `<blockquote></blockquote>`; the check runs before any token is emitted, and non-empty runs including ones with internal blank quote rows keep their original token stream. C3 (fossil-era artifact manifesting as a reference bug) changed the newline after a lower-depth end token from one newline to two in the parse rule: with one newline the Paragraph rule never formed a paragraph for the first line back at the lower depth, so the reference emitted a bare `<br />` followed by bare text where live and ftml emit `<p>...</p>`. Live settles this in cached probe muse-probe-r2block-bq-nested-mixed (`> a` / `>> b` / `> c` gives `<p>c</p>` after the inner close) and in the native corpus pin, and the change touches exactly the three battery cases bq14-mixed-down, bq15-mixed-updown and bq45-unterminated-deep and the one probe nested-mixed. Pre-correction bytes are preserved as Blockquote.parse.before.php (SHA-256 c4ffaa9af0324da3a2a673dfd342af4a9ff373875f5305123e4486d5963c17bb) and Blockquote.render.before.php (SHA-256 70bbf934296a4995c5f6fcf14f34ef9e95eb7af510c785bc3ac3e27bd7d38b44); the corrected files are SHA-256 9294382a3d995092b51d9c31d560836a5fafe815765ca300909a8388dd21f84a (parse) and 8f1de52c7730665e1ceedcf4e0b01a7215f0699e27c96990642ef0c314ee3400 (render), both passing php -l. Both digests are recorded in before-sha256.txt and after-sha256.txt in this directory.

Remaining disagreements and dispositions. Live's newline pretty-print around `<blockquote>`, `<p>`, `<div>`, `<ul>` and headings, the trailing newline after `</blockquote>`, and ftml's `<br>` where live and the reference use `<br />` are serving-layer and frame-level surfaces, not Blockquote divergences; this stage did not try to reproduce the live serializer's newline injection. No new candidate ftml divergence was found in this rule's matching space: every shape the battery and probes exercise (line-start anchoring, tight versus spaced marker runs, depth arithmetic including skips and decreases, no-space and bare markers, empty runs, adjacency, and the literal block forms) is agreed by ftml and live structurally, so there is no new M-style finding for the coordinator to route; the `<br>` spelling observed here is consistent with the already-routed M33 family and is not renumbered. A question arose about whether the live serializer's pretty-print newlines should be copied into the reference; the assumption proceeded on was that they are serving-layer frame surface owned by later rules and the live page serializer, so structural comparison is the rule-level measure and no newline-injection emulation was added.
