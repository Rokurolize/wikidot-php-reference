# R2 Blockquote/Heading/Toc stage: Heading rule section (2026-11-20)

Mechanism as corrected. The parse rule's regex is now `/^(\+{1,6})(\*?)[ \t]+(.*)/m`: group 1 is the one-to-six plus run that fixes the heading level, group 2 is an optional `*` immediately after the plus run that marks the Wikidot no-toc form, and group 3 is the heading text after a run of one or more spaces or tabs. The fossil's `/^(\+{1,6}) (.*)/m` consumed exactly one space and knew no `*` suffix, so it left every `*`-suffixed heading as literal paragraph text and kept the second space of a multi-space prefix as the first character of the heading body. For a `+` heading the process method allocates an anchor `id` as `htmlspecialchars(id_prefix) . $this->wiki->vars['headline_id']`, with `id_prefix` configured as `toc` and the counter initialised to 0 when null; it emits a Heading start token of type `start` carrying `{type, level, text, id}`, emits an `end` token carrying `{type, level}`, and increments the counter. For a `*`-suffixed heading it emits type `start-notoc` with the same fields but `id => null` and does not increment the counter. The surrounding source is still replaced by `"\n" . start . text . end . "\n\n"`. The render rule keeps the fossil's `<hN>` markup and `<span>` wrapper but now derives the id attribute as `' id="' . $id . '"'` only when `use_id` is true and `$id` is set and non-empty, so an anchored heading renders `<hN id="tocK"><span>` and a no-toc heading renders a bare `<hN><span>` with no stray space; the `end` token still renders `</span></hN>` followed by a newline. The distinct `start-notoc` type is deliberate: the Toc parse rule iterates `getTokens('Heading')` and skips every token whose type is not exactly `start`, so no-toc headings are absent from the table of contents without any edit to Toc.php, which is outside this lane's scope. A token dump of probe p09 confirms the seam: the Heading tokens are `start` A with id toc0, `end`, `start-notoc` skip with null id, `end`, `start` B with id toc1, and the Toc tokens are exactly two item_start tokens with ids toc0 and toc1.

Anchor computation reported for the coordinator. Anchors are positional, never derived from heading text: the counter starts at 0, increments once per `+`-suffixed heading in document order, and is not touched by `*`-suffixed headings, by intervening paragraphs, or by repeated text. Three consecutive `+ Same` therefore produce ids toc0, toc1 and toc2, confirmed by live probe muse-probe-r2block-head-p03-same-text and by battery case h21-same-text. The Toc rule copies the heading start token's `id` into each `item_start` token and uses the token's raw `text` as the link label, numbering its `count` from 0; live probe p18 and battery h25 through h27 show the resulting `#toc0`, `#toc1`, `#toc2` links. ftml's equivalent is `Heading::html_tag()` in src/tree/heading.rs, which calls the render indexer only when `has_toc` and formats `toc{index}` from zero, and `push_table_of_contents_entry` in src/parsing/rule/impls/header.rs, which is also gated on `has_toc`; the corrected reference agrees with that model on all 22 live probes. One seam root still owns: Toc link labels come from the raw heading token text, so inline markup inside a heading is visible as wikitext in the TOC entry, and root's cross-rule battery should settle whether live escapes or renders that markup before anyone changes Toc.php.

Corrections made and classified. C1 is the no-toc `*`-suffixed heading form in both owned files, classified as a fossil-era artifact: the fossil grammar predates Wikidot's no-toc heading suffix, and live is settled by valid probes muse-probe-r2block-head-p01-notoc-single (`+* no toc one` renders `<h1><span>no toc one</span></h1>` with no id), -p02-notoc-interleaved, -p09-toc-excludes-notoc, -p17-notoc-repeat and -p21-notoc-two-spaces, with ftml's own pin test/heading/basic agreeing. The Toc owner independently settled the same shape from the other side of the seam with the live probe muse-probe-r2block-toc-p13-skipped and battery case toc10-skipped-heading, which show `+* Skipped` as an unnumbered heading on live and in ftml while the pre-correction fossil left it literal, with all three sides still excluding it from the TOC and assigning identical anchors to the surrounding headings; that is the same fossil-era artifact as C1 and is already fixed by this rule's parse and render edits, so it yields no candidate finding and no further edit. C2 is the parse-side consumption of the whole horizontal-whitespace run after the prefix, classified as a fossil-era artifact manifesting as a reference bug: live probes -p13-double-space (`++  two spaces after prefix` yields `two spaces after prefix`), -p19-tab-after, -p20-three-spaces and -p21-notoc-two-spaces settle that every space or tab between prefix and text is dropped, while the fossil kept all but the first. C3 is the render-side id attribute handling, classified as a reference bug exposed by C1: the fossil emitted a literal space after `<hN` even when no id was present, which would have produced `<h1 ><span>` for the newly supported no-toc form, whereas live emits `<h1><span>`; the id is now emitted only when present. Pre-correction bytes are preserved as Heading.parse.before.php (SHA-256 a9088e7493e7925532baa686db18e739d4789d23192c270eb1f122186470c561) and Heading.render.before.php (SHA-256 7b6320a090583b51dc3e9149a2a614abc2bf94269eaec0afb822f6cce162078b), with after digests SHA-256 88650648749ce0f04da7ebb569e816a88399ea2f4a4dafc5796c39f04c0e3377 for parse and 2968bc44d47cc01288f8f4a165a42dd7c8544148b4641365ca5e614850daf5f3 for render; both corrected files pass `php -l`. The correction changes exactly 14 of 55 battery render outputs and 8 of 22 probe render outputs, all of them no-toc forms, multi-space or tab prefixes, or TOC-bearing documents whose anchors and entry set shift accordingly.

Remaining disagreements and their dispositions. Two attempted probes, a source of `+ ` and one of `++ trailing  `, could not be saved because Wikidot strips trailing whitespace on the anonymous saved-page round trip, so those shapes (battery h40 and h41) are serving-layer save-normalization cases that live cannot settle and no finding is claimed for them; ftml's empty-heading normalization also drops the inner `<span>` on h40 and h52 where the reference keeps it, again without live evidence. Frame-level surface owned by later rules accounts for the remaining whole-string gap: newline padding around headings, `<div >` versus `<div>`, `<br />` spelling, ad-script and page-footer fragments in one captured page, and the pretty-printed newlines in live's TOC table are not Heading output and were not touched. Four numbered findings remain for the coordinator to route, each with live evidence rather than a guess: H1 is a candidate ftml divergence where ftml serializes an apostrophe in heading text as `&#39;` while live and the corrected reference emit a raw `'` (probes -p08-entities and battery h19-entities); this is the already-known M28 root cause and should be consolidated rather than renumbered. H2 is a candidate ftml divergence where ftml tokenizes `[[http://example.com|the site]]` into `[[<a href="http://example.com">http://example.com</a>|the site]]` while live and the reference emit `See [<a href="http://example.com|the">site</a>]` (probe -p07-external-link, battery h16-external-link); an inline-cases check shows the same split in a plain paragraph, so this is a Link-rule surface to route to the Link owner, not a Heading defect. H3 is a candidate reference divergence owned by another rule: live and ftml render `[[a name="x"]]anchor[[/a]]` inside a heading as `<a href="">anchor</a>` while the reference leaves the call literal (probe -p22-anchor-element, battery h18-anchor, and the same split in a plain paragraph), so the Anchor rule owns it and no Heading edit was attempted. H4 is a candidate reference divergence owned by the Div or barrier layer: an inline `[[/div]]` on a heading line makes live and ftml split the heading into `<span>Head</span> tail` with a nested span on the next heading, while the fossil keeps the whole line inside the heading span (probe -p23-div-barrier-inline, battery h48 and h54, and ftml's own pin test/heading/barrier-toc-raw); implementing barrier splitting in Heading.php would need an unsound raw-wikitext heuristic outside this rule's token contract, so it is routed rather than patched.

Questions asked and assumptions proceeded on. The only design question was whether Toc.php should be edited so a no-toc heading is excluded from the table of contents; the assumption was no, because emitting a distinct `start-notoc` token type lets Toc's existing exact `type == 'start'` filter do the work inside this lane's two-file scope, and the p09 token dump verified the assumption rather than leaving it as a claim. The second question was how to treat sources whose trailing whitespace Wikidot removes on save; the assumption was to keep them in the battery, drop them from live probing, and classify them as serving-layer save normalization with no live-backed finding, which is recorded above. No ftml file, shared harness file, other rule file or git state was changed, and no git identity or author variables were set.
