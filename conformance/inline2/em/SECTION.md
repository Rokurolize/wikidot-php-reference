# R2-INLINE2 section: Emphasis (pipeline rule 46)

## Mechanism as corrected

Emphasis pairs `//` markers first-fit within a line chunk, so each opener binds the earliest following `//` that is not separated by a paragraph break; a body is accepted only when it is empty or opens and closes in non-whitespace, and a whitespace-padded body such as `// padded //` stays literal. An empty body between two adjacent markers is a real pair that renders as nothing: the parser consumes both markers and emits no Emphasis token pair, which is what makes `////`, `////four////` and `////em////` collapse to nothing, `four` and `em` respectively. Non-empty pairs emit an Emphasis start token and an Emphasis end token around the unchanged body, and the Xhtml render maps them to `<em>` and `</em>` with the optional css class hook; the render file needed no change. Because the shared harness applies Colortext, Strong and then Emphasis after the Url rule has already tokenized scheme URLs, an unpaired protocol-relative form like `//example.com/a` stays literal while `//example.com/a//` pairs its own two `//` markers into italics; live, the reference and ftml agree on both. The fossil hypothesis that `//` pairs collide with URLs is therefore a non-issue at this rule: the collision is resolved by rule order, not by anything in Emphasis. Crossed `//**...//**` and `//**one **two//**` forms are decided by the Stage-2 lowering stack on live and in ftml, where each construct first pairs its own markers and the stack then nests them; the reference's Stage 1 has no such stack, so its token order yields misnested tags there, which this stage records as frame-level rather than patching.

## Corrections and classifications

C1 is the only correction and it is confined to ref-php/text-wiki/Text/Wiki/Parse/Default/Emphasis.php. The fossil regex `/\/\/([^\s](?:.*[^\s])?)\/\//U` was replaced with `/\/\/(.*)\/\//U` under the U (ungreedy) modifier so the earliest closer wins, and process() now returns an empty string for an empty body and returns the original matched text unchanged for a body that starts or ends in whitespace. Classification: fossil-era artifact at the Stage-1 first-fit pairing surface, equivalently a reference bug there; live settled it and ftml's own first-fit token scan independently confirms it. Live evidence is the pages muse-probe-r2in2-em-em09, -em12 and -em14 (`////four////` renders `<p>four</p>`, `////` renders empty, `////em////` renders `<p>em</p>`), and the ftml corpus pin test/bold/empty-pair-feeds-later-rule pins the same empty-pair drop. At token level the before capture showed phantom Emphasis start/end tokens wrapping `//four` and `//em` on em09 and em14 and none on em12, while the after capture shows no Emphasis tokens on any of the three and the source markers consumed. No Emphasis render rule was edited, so EmphasisXhtml.before.php is a verification record only and its SHA-256 still matches the live file. One change in the after capture is not mine: the Colortext owner removed the trailing semicolon from the color style in the Xhtml render at 17:47:24, which is why em26 moved from `<span style="color: red;">` to `<span style="color: red">` between my before and after runs; that correction belongs to that owner's section and is not counted here.

## Remaining disagreements and dispositions

em12 `////` still differs as `<p></p>` from the reference against an empty live and ftml body; this is a frame-level rule-ordering surface because the Paragraph rule wraps the source before Emphasis consumes it and empty-paragraph suppression is Paragraph-owned, so it is not patched here and is left for root or the Paragraph layer. em23 `//**crossed//**` and em29 `//**one **two//**` are misnested by the reference (`<em><strong>...</em></strong>`) while live and ftml both render proper nesting (`<em><strong>...</strong></em>`); this is the Stage-2 lowering-stack surface named in the 2026-11-04 ruling and is recorded as frame-level, not patched, because the reference Stage 1 has no repair stack. em32, em33 and em34 are all-three disagreements confined to paragraph and div whitespace: the reference emits `\n\n` between paragraphs and `<div >` with extra newlines, live emits a single `\n` and clean `<div>`, and ftml emits no separator at all; these are Paragraph, Div and Block renderer surfaces outside this rule and are not patched. em46 `{{ //code literal// }}` leaves padding spaces inside `<tt>` in the reference while live and ftml drop them, a Monospace or Tt rule surface from the earlier CODE stage. em44 `[[http://example.com|//link label//]]` and em47 `[[code]]` are cases where the reference agrees with live and ftml diverges, so they are routed as candidate ftml findings below rather than as reference corrections; em44 is also a link-label interaction that root owns. The raw `<br />` in the reference and live against `<br>` in ftml on em30, em31 and em48 is normalized away in the three-way buckets but remains a raw rendering-layer difference, noted as a candidate finding. No disagreement was called a reference bug on a shape live had not settled: every correction above has a live capture behind it.
