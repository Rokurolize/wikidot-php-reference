## Mechanism as corrected

Parse rule (ref-php/text-wiki/Text/Wiki/Parse/Default/Comment.php). The fossil regex /(\n)?\[!\-\-(.*?)\-\-\]/si is unchanged: the span is case-insensitive, dot-all, may carry one leading newline, and process() still returns the empty string without emitting a token in the ordinary case. The corrected parse() runs the same regex with preg_match_all and PREG_OFFSET_CAPTURE so it can inspect the match offset. When a comment is alone on its line apart from leading spaces or tabs and only whitespace or end-of-line follows its closer, the rule removes that indentation and substitutes a Comment token in its place; the token renders to the empty string, so the line survives for the paragraph rule as an empty line instead of becoming a visible run of spaces or disappearing into a paragraph break. This reproduces the saved live page muse-probe-r2next-comment-nl-indented-spaces, where a\n  [!-- c --]\nb renders as <p>a<br />\n<br />\nb</p>. Tabs have already become four spaces in the shared Prefilter before Comment runs, so the tab-indented battery case takes the same path. All other comment shapes, including the double-bracket form, unterminated openers, stray closers, extra closer hyphens, nesting, adjacency and comments inside Code/Raw/Module-protected regions, keep the fossil behavior.

Render rule (ref-php/text-wiki/Text/Wiki/Render/Xhtml/Comment.php). It is unchanged and byte-identical to Comment.render.before.php. It was vestigial in the fossil because no rule ever emitted a Comment token; after C1 it is the renderer that turns the indented-line placeholder into no visible text, which is exactly its existing token() contract of returning ''.

## Corrections made

C1 (fossil-era artifact manifesting as a reference bug). The fossil left the indentation before a comment-only line in the source, so the reference rendered two literal spaces where live renders an empty line. The deciding evidence is the valid live probe muse-probe-r2next-comment-nl-indented-spaces (stable=true, saved_source_matches=true), corroborated by the ftml corpus pin paragraph/comment-line-break-demotion and the battery case nl-indented-spaces. The corrected parse() removes the indentation and emits an empty-rendering Comment token as described above. It changed two battery render outputs, nl-indented-spaces and nl-indented-tab, and one probe output, nl-indented-spaces; no other Comment-owned output moved. Pre-correction bytes are preserved as Comment.parse.before.php (SHA-256 a434400a0dd11b779f68ffdff54c65c387626ca0e7103a004b6bbbf7b975ef7d) and Comment.render.before.php (SHA-256 9a61fec99ef3fa4128a6f8a8686abea30db42fcbea9ede5f1d746a1a1831da72), and cmp verified both against their sources before editing.

No PHP-version artifact and no harness matter required a correction. A question arose mid-work about the double-bracket form: the ftml pin test/comment/double-bracket-comment-head/wikidot.html shows the brackets elided, so I tried an experimental outer-bracket correction and then ran the three live probes. Live left the literal [] in all three, so live settled the question against the experiment; I reverted it completely before the final runs and proceeded on the assumption that the saved page view governs this shape. The raw render diff therefore shows only the two C1 battery cases plus adj-before-date, which changed because the Date rule owner edited ref-php/text-wiki/Text/Wiki/Parse/Default/Date.php and Render/Xhtml/Date.php concurrently in the shared tree; that change is not Comment-owned and was not made or reverted here.

## Remaining disagreements, dispositions, and candidate findings

Class S (frame-level surface owned by later rules or the pipeline frame, not Comment divergences). The reference's unconditional trailing \n\n around rendered content, its <br /> versus ftml's <br>, and its four-space <li> indentation are the familiar join-surface differences; nl-comment-only-blank-around, adj-before-div, adj-inside-code and the heading and list probes are classified here, and live agrees with the reference on the probed ones after normalization. adj-inside-span-head and pin-double-bracket-before-name differ by the fossil's double space and empty style attribute in span heads, which belongs to the span/div head rules later in the pipeline. adj-before-iframe differs by one space before the closing > of the iframe tag, which belongs to the Iframe rule owner; both are listed in x-notes.txt and neither was corrected here.

Serving-layer scope. adj-before-date and ml-span-with-module-opener exercise what a date and a known module compute from page or site state; as in earlier stages that expansion is out of scope, and only the matching, tokenizing and observable display shape are owned here. The reference's simultaneous date-format change in adj-before-date came from the Date owner's concurrent edit, not this lane.

F1 (candidate ftml divergence, route to coordinator). For the double-bracket comment form [[!-- ... --]], ftml's preproc/comments.rs double_bracket_comment_span removes the enclosing brackets, and its corpus pin test/comment/double-bracket-comment-head/wikidot.html shows <p>Body paragraph.</p>. Live disagrees: the valid probes muse-probe-r2next-comment-pin-double-bracket-head, -pin-double-bracket-inline and -pin-double-bracket-only-line render <p>[]<br />\nBody paragraph.</p>, <p>Before [] after.</p> and <p>Line one<br />\n[]<br />\nLine two</p>, exactly the fossil and corrected reference shapes. The three corresponding battery cases are pin-double-bracket-head, pin-double-bracket-inline and pin-double-bracket-only-line. Live wins, so no reference change was made; pin-double-bracket-in-block-head confirms that the inner-span-only behavior also agrees with live and ftml when the comment sits in a block head.

F2 (candidate ftml divergence with a live-settlement caveat, route to coordinator). For a lone CR as the line ending around a comment, the harness input stage normalizes CRLF but leaves the lone CR for Prefilter, which converts it to LF before Comment; ftml's preproc keeps a lone CR as a paragraph boundary, so battery case cr-only-line differs (<p>a<br />\nb</p> versus <p>a</p><p>b</p>). Wikidot normalizes line endings on save, so no saved-page probe can settle this shape; it is a harness and whole-pipeline convention, not a settled reference error, and no correction was made. Comment-inside-include-arguments is excluded by design as already adjudicated in GRAMMAR-INCLUDE.md and R2-INCLUDE.md.
