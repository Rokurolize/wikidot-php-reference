Reference correction to Url escaping (2026-11-22), settled by the live probes muse-probe-htmlchars-url-desc, url-star and url-auto (all valid, stable, saved_source_matches): a described link `[https://example.com/a'b?x=1&y=2 O'Brien &amp; <x> "q" é]` renders on live with the apostrophe raw in both the href and the text, the ampersand escaped, the authored entity double-encoded, and <, >, " escaped in the text, exactly `htmlspecialchars(..., ENT_COMPAT, 'UTF-8')`; the starred form keeps `target="_blank"`; and the bare autolink control shows the apostrophe stays outside the token (`</a>'z`), confirming the parse-side boundary. Reachability is asymmetric by call site, and the probes follow it: an inline autolink href can never contain an apostrophe (the Url regex excludes `'` from every segment), but a described href can (the liberal regex's final segment admits it), and a described text can contain every differing class. The fossil's Render/Xhtml/Url.php used bare `htmlspecialchars()` at four call sites (href, image-branch text, regular text, target), which on the harness's PHP 8.5.4 defaults to ENT_QUOTES|ENT_SUBSTITUTE and spelled reachable apostrophes `&#039;`. The change is confined to Render/Xhtml/Url.php: all four calls now pass ENT_COMPAT, 'UTF-8'. The target call's only reachable values are the constant `_blank` (set by the parse rule for starred forms, or render configuration) and the image branch is disabled in the harness configuration, so those two conversions are output-neutral and are made only so no bare call remains in the file. The only behavioral difference from the bare call besides the apostrophe is invalid-UTF-8 handling (empty string instead of U+FFFD substitution), unreachable because href and text are substrings of a saved page's UTF-8 source.
