# CORRECTION-REFCORR51 — block-open grammar: stray div closers, html head attributes, duplicate attributes

REFCORR51 is the conformance record for the hunt-blockopen sweep. It uses byte-verified saved-page sandbox evidence on `sandbox-for-codex`; the probe pages are immutable evidence and remain in place. No production page was accessed. The lane used 12 probe-page cycles: five grouped matrices (48 labeled cells), four isolated stray-div discriminator documents, and three isolated html discriminator documents.

## Finding 889 adjudication — stray div closer and the fake local anchor

Fresh isolated saved-page evidence refutes the triage's assumed live fake anchor for the exact div shape. The documents `[[/div]] [[div]]b`, `[[/div]] [[div]]a[[/div]]`, and `[[/div]]  [[div]]b` all serve the literal collapsed form `[[/div]][[div]]...`; no link is formed. The reference already had this behavior, so no correction is made for finding 889.

The measured token rule is narrower than "every stray closer plus opener pair feeds the local-anchor scanner". The fossil Divprefilter consumes horizontal whitespace in the exact `[[/div]]...[[div` sequence before the Url rule runs, so the simple div pair has no separator byte from which the described-local-link grammar can be built. When the opener carries attributes, the whitespace inside that opener still permits the Url scanner's malformed described-link form: `[[/div]] [[div class="x"]]b` serves href `/div]][[div` with label `class="x"`. Non-div controls such as span, html, foo, and mixed close/open names do form the fake local anchor because no div-specific prefilter removes their separator. These controls were already reproduced by the reference and are pinned as mechanism evidence.

One adjacent shape is not claimed: in `[[/div]] [[div]]\nx\n[[/div]]`, both sides suppress the fake anchor and open the valid div, but live serves a newline/space boundary between the literal stray closer and the following `<div>` while the reference emits them adjacent. That is a generic valid-div block-boundary framing residue, not evidence for the fake-anchor mechanism, and is recorded as a remainder rather than folded into this correction.

## Finding 903 adjudication — malformed html heads

Fresh saved-page evidence also refutes the triage's assumed live literalization of malformed html heads. Every measured head shape forms the html iframe, including bare words, unquoted values, single-quoted values, empty heads with trailing spaces, unclosed quotes, spaced equals signs, and mixed well-formed/malformed tokens. No head-token shape in the 20-cell matrix made the block literal. Because that conflicted with older integration fixtures, three exact-input saved-page discriminators were also captured: the standalone `[[html stray]]\nX\n[[/html]]` document, the standalone `[[html x]]y[[/html]]` document, and the full concatenated head-arguments sequence. The concatenated fixture file ends in a newline that Wikidot save read-back does not preserve, so that discriminator is captured as the same sequence without only that final newline; the normalization is recorded in the lane map. All three form iframes throughout, including every malformed head in the concatenated sequence. The reference already recognized the block on all those shapes, so no recognition correction is made.

The malformed-head attribute boundary is nevertheless real and is corrected at the attribute-parsing layer. Live's behavior follows the fossil `getAttrs` grammar: only lowercase `name="value"` assignments parsed by that shared accumulator become html `class` or `style` values. A malformed token before a well-formed assignment contaminates the key and causes the later assignment not to be propagated (`stray class="a"`, `style=color:red class="a"`, single-quote-first, and spaced-equals forms all serve no authored class). A well-formed assignment followed by a malformed trailing bare token remains effective (`class="a" stray` keeps `class="a"`). Uppercase `CLASS="a"` forms the iframe but is not propagated as `class`. Arbitrary well-formed names such as `data-x`, `id`, `width`, and `title` do not prevent recognition but are outside the html block's emitted class/style surface.

## Finding 905 correction — duplicate attributes are last-wins at the shared attribute layer

Live keeps the last duplicate value on html: `class="a" class="b"` serves `class="b html-block-iframe"`, the style sibling serves the second style, three repeats serve the third value, and an interleaved duplicate still uses its last value. This is not html-specific. The same last-wins behavior is live-pinned for the duplicate-using attributed controls measured in the matrix: `[[iframe ... width="100" width="200"]]`, span class, div class, and anchor href all keep the second value. That is exactly the overwrite behavior of the fossil's shared `getAttrs` accumulator.

The correction therefore replaces the Html rule's independent first-match `preg_match` extraction with the shared `getAttrs` parse and then reads lowercase `class` and `style` from its result. This is a single-layer correction in `text-wiki/Text/Wiki/Parse/Default/Html.php`. It intentionally has two measured collateral effects on the same html-head grammar: malformed-token key contamination now suppresses later class/style propagation exactly as live does, and uppercase attribute names are no longer propagated case-insensitively. Those effects are pinned rather than silent.
