# R2-notes Bibcite rule: differential, correction, and section (2026-11-20)

Method. I compared three sides over one 60-case whole-document battery and one 18-case live probe set. The reference side is the shared read-only harness ref-php/harness/batch.php in modes render and tokens, run with /usr/bin/php; root's disclosed per-case reset of footnotes, bibitems and bibitemIds is in that harness, and every stderr sidecar I produced is empty. The ftml side is the one shared dumper at conformance-refphp/notes/rust-dump/target/release/r2notes-rust-dump over JSONL {"id","source",optional "tags"}, at the read-only checkout HEAD 6a029bf416651e0d68408f7c977b4cae30ebec55 recorded in conformance-refphp/notes/rust-dump/FTML-HEAD.txt. The live side is 18 saved anonymous page views on sandbox-for-codex.wikidot.com under prefix muse-probe-r2notes-bibc-, created and captured with the bundled wikidot-probe CLI through scripts/wikidot-python; all 18 captures are valid, stable across two independent anonymous GETs and saved-source matching, and a first unchunked capture pass aborted on a transient ConnectTimeout after 10 pages, so I reran the full set in four chunks with retries and merged the results without padding any validity. The evidence order was ftml corpus pins, then frozen captures, then live probes, and live behavior won every disagreement it settled. I also ran the reference harness and the dumper over the probe sources so all three sides are cached side by side. The battery is reproducible with make_battery.py, the probes with make_probes.py, the capture with run_capture.sh, and the numbers with compare.py; the full report is compare-report.txt, with the raw per-case tables in compare-before.txt and compare-probe-before.txt. One question arose mid-work and is recorded here: whether to fabricate a deterministic id suffix in the reference so that it would byte-match ftml's bibcite-1-81349a. I proceeded on the assumption that an unpredictable per-save DOM id is serving-layer scope and that inventing a fixed value would only replace one non-matching byte string with another, so I made no such change; the reasoning and the live evidence are in S1 below.

## Mechanism as corrected

Parse rule (ref-php/text-wiki/Text/Wiki/Parse/Default/Bibcite.php). The file is byte-identical to its pre-correction state (SHA-256 7ac06082bcc29162df265d87cc05f2c33538f3c3b06b8b862d67948dfd983cb0) and was not edited. Its regex /\(\(bibcite\s([a-z0-9]+)\)\)/i requires the double-parenthesis opener, a case-insensitive `bibcite` marker, exactly one whitespace byte, an ASCII alphanumeric label and the closing `))`, and emits one Bibcite token whose only option is the label. Because Bibcite runs after Bibliography in the rule order, a citation inside a bibliography body still forms after that rule joins the body into one line, and because the rule matches anywhere it resolves forward or backward references equally. Text_Wiki's prefilter expands a tab to four spaces, so `((bibcite<TAB>Tabbed))` leaves the call literal; two or more spaces leave it literal for the same reason, while a newline is accepted as the single `\s` and the citation resolves. Comment removal runs earlier, so `((bibcite k[!--x--]ey))` resolves against the label key, while an empty label, a missing close, a second word, a pipe, a hyphen, an underscore, a bold label, a non-ASCII label, a second `bibcite` word and the closer-only form remain ordinary literal text. Battery cases bibc-12, bibc-13, bibc-19 through bibc-35 and live probes p-two-space, p-three-space, p-tab-sep, p-newline-sep, p-empty-label, p-comment-label and p-malformed settle all of these; the reference matched live on every one of them.

Render rule (ref-php/text-wiki/Text/Wiki/Render/Xhtml/Bibcite.php). The file is byte-identical to its pre-correction state (SHA-256 bd8c1fb65cd425fc837dba0db4a937087e01df3a971af5657abf217983273fdc) and was not edited. It looks the token's label up in wiki vars bibitemIds, which the Bibitem parse rule populates with one-based numbers in definition order; a missing label produces the inline error span `<span class="error-inline">Bibliography item <em>label</em> not found.</span>`, and a present label produces `<a href="javascript:;" class="bibcite" id="bibcite-ID" onclick="WIKIDOT.page.utils.scrollToReference('bibitem-PREFIXID')">ID</a>`, where PREFIX is the xhtml bibitem id_prefix render configuration (unset in this harness, so empty). Duplicate labels keep the last definition's number without advancing numbering for later labels, so bell, bell, guy number 1, 2, 2 and citations to bell and guy both resolve to 2; this is confirmed on three sides by battery bibc-08 and live p-dup-label, and the ftml corpus comment in src/tree/bibliography.rs records the same live capture. Case mismatch stays unresolved (bibc-10, p-case-mismatch), an empty bibliography or no bibliography keeps the error span (bibc-15, bibc-16), and a citation to an entry defined later resolves because Bibitem has already run over the whole document (bibc-05, p-id-forward). The block spelling `[[bibcite alpha]]` and its score variant `[[bibcite_ alpha]]` stay literal on live even when a matching entry exists, and the reference and ftml agree (bibc-49 through bibc-51, p-block-defined, p-block-score-defined); that surface belongs to a different rule family and was not added here.

## Corrections made

No corrections were made, so no classification of a correction applies. I preserved the pre-correction bytes of both files anyway as BibciteParse.php.before.php and BibciteRender.php.before.php, with SHA-256 values recorded in before-sha256.txt, and verified that the current files and the preserved copies hash identically. I state the absence of corrections positively rather than padding the section with an artificial change: on the 60-case battery and the 18 live probes the fossil Bibcite rule already reproduces live's matching space, label alphabet, forward and backward resolution, duplicate-label numbering, undefined-label error span, literal malformed forms and the exact bytes of the anchor element apart from the serving-layer id suffix discussed below. The only side that differs from live on the rule's own surface is ftml, and the standing rule forbids changing either ftml or a reference rule on a shape where live and the fossil already agree. The two reference snapshot pairs are byte-identical under cmp, so ref-render-after.jsonl and ref-tokens-after.jsonl are copies of the before files, and neither rule-file hash changed from the start of the stage.

## Remaining disagreements, dispositions, and candidate findings

Class S (frame-level surface owned by later rules, not Bibcite divergences): the reference's trailing `\n\n` after a paragraph versus live's and ftml's tighter framing, the `<br />` versus `<br>` spelling, the div and span attribute padding, the internal link's `class="newpage"` on bibc-42, the `&#8212;` versus `—` typography on bibc-58, and the fact that the fossil reference does not form the `[[a href=...]]` outer anchor at all on bibc-52 and p-anchor. The inner spacing of the bibitems shell, the empty-entry trailing space and the residual-paragraph layout on bibc-57 belong to the Bibliography and Bibitem owners; entry numbering and duplicate resolution themselves agree on all three sides, so no correction in another rule's file was discovered, and this is reported to root for the catalog rather than edited here.

Class T (serving-layer scope): S1, the per-save random bibcite id suffix. Live emits ids such as bibcite-1-82730a on muse-probe-r2notes-bibc-p-id-defined, bibcite-1-81110a on p-id-forward, bibcite-1-73487a and bibcite-2-67729a on p-id-two-cites, and bibcite-2-94473a and bibcite-2-57516a on p-dup-label. Repeated anonymous fetches of one saved page return the same suffix, but pages with equivalent source semantics have different ones, so the value is generated at page-render time and is not a function of wikitext. The reference emits bibcite-1 with no suffix and ftml emits its fixed-seed bibcite-1-81349a; both differ from live only in that value while agreeing on index, scroll target, visible number and attribute order. No implementation can reproduce the live digits from this input, so I left the deterministic reference stand-in intact and routed the disposition to root rather than calling either side wrong on an uncopyable value.

F1 (candidate ftml divergence, route to coordinator and assign an M-number continuing from R2-LINK's M27). ftml's HtmlContext escapes the single quotes of the onclick attribute to &#39; while live and the reference emit the raw quote; live settles this byte-for-byte on the seven anchored probes p-id-defined, p-id-two-cites, p-id-forward, p-dup-label, p-comment-label, p-anchor and p-footnote, and ftml's own pin test/footnote/comment-bibcite-label/wikidot.html contains the entity. This is the same serializer split the Equationreference owner already routed, and no ftml file was edited.

F2 (candidate ftml divergence, route to coordinator). ftml accepts two or more spaces between `bibcite` and the label while live leaves the call literal; live p-two-space and p-three-space and battery bibc-13 settle it, and ftml's test tests/wikidot_inline_bibcite.rs asserts the opposite of live for `((bibcite   A9))`.

F3 (candidate ftml divergence, route to coordinator). ftml accepts a tab separator while live leaves the call literal because Text_Wiki's prefilter expands the tab to four spaces; live p-tab-sep and battery bibc-12 settle it, and ftml's test asserts the opposite of live for `((bibcite\tTabbed))`.

F4 (candidate ftml divergence, route to coordinator). ftml rejects a newline separator while live resolves the citation through PHP's `\s`; live p-newline-sep and battery bibc-33 settle it, and ftml's inline rule lists `Token::LineBreak` among its invalid conditions. F2 through F4 share one ftml separator-handling cause against live's ordered-regex behavior.

Coverage gaps are stated rather than padded. Nested bibliography labels, citations inside suppressed Iftags bodies and numbering across multiple bibliographies in one page are root's cross-rule integration and were noted rather than owned here; the per-rule probes deliberately kept one bibliography per page for those shapes. The block bibcite spelling was probed only in the Wikidot layout used by the shared dumper, which is live's layout, not the Wikijump layout where ftml's separate block rule forms a bracketed citation. No ftml file, shared harness file outside root's disclosed reset, git commit or git identity variable was changed by this rule owner. The 18 probe pages are left in place on sandbox-for-codex.wikidot.com and listed with their exact sources in probe-map.json and findings-for-root.txt; no credentials were printed in any evidence file.
